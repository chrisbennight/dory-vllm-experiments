# Dory performance research — 18 October 2026

The strongest next direction is to reuse a weight read across speculative tokens
from one user. Dory's shared recurrent block makes mixed-depth speculation a
particularly good fit. Further single-token kernel work remains useful, but the
current byte model leaves about 37% throughput headroom at the 640-token profile
point. Larger gains require changing the bytes read per accepted token, the
precision contract, or the hardware bandwidth.

This investigation combines a review of local code and measurements with
primary-source research through Exa and GitHub. It adds CPU analysis; GPU
measurements below come from the existing experiments. The proposals have not
been benchmarked on a GPU or evaluated for task accuracy in this investigation.
For subsequent results, see the [experiment log](../../EXPERIMENTS.md).

The local measurements establish the following starting point:

| Configuration and measurement | Result | Evidence |
|---|---:|---|
| Unmodified vLLM, Triton attention, 128 input / 1024 output, one user | 161.7 tokens/s | [Serving confirmation](../confirmation_after_e5.md) |
| Fused path after E5, same serving workload | 199.2 tokens/s | [Serving confirmation](../confirmation_after_e5.md) |
| Fused path after E9, 640-token prompt, two loops, BF16 head | 5.05 ms/token, about 198 tokens/s | [Latest reviewed profile](../profile_20261018T183509Z_nvfp4_loops2_prompt640_triton_attn/report.md) |
| INT8 head after E7, before E9 | 4.73 ms/token | [Experiment log](../../EXPERIMENTS.md#e7-8-bit-lm-head-for-single-token-logits-2026-10-18---kept-opt-in) |

Serving throughput includes prompt processing and request overhead; the profile
is steady decode. The INT8-head result and E9 result are separate measurements,
so their gains must not be added and presented as an observed configuration.

In the E9 profile, weight GEMVs take 3.771 ms, the BF16 head 0.702 ms and
attention 0.430 ms. Everything else, including idle time, takes about 0.151 ms.
The GEMV category includes fused normalization and residual work: its 76%
effective bandwidth does not establish that its remaining time is all a DRAM
problem. Actual memory counters and instruction stalls are needed to distinguish
dequantization, register pressure, reductions and memory latency.

The byte calculation uses the checkpoint's actual dimensions: hidden size 2560,
intermediate size 7168, 16 query heads, four KV heads and head dimension 256.
The 72 configured layers are individual attention or MLP sublayers, whereas the
model card's 36 layers are attention/MLP pairs. With two loops, execution visits
16 input + 2 × 40 recurrent + 16 output sublayers: 112 sublayers, comprising
56 attention applications. Fourteen use full attention and 42 use a 1024-token
window.

NVFP4 stores 0.5 weight bytes plus 1/16 scale bytes per parameter. The main
projection matrices therefore require 2.890 GB per decoded token, including
repeated recurrent reads. The BF16 head adds 0.671 GB. At the profile's mean
context of 672 tokens, KV reads add 0.154 GB. At 1008 GB/s these sum to about
3.70 ms, including the existing analysis's 0.01 ms allowance for small tensors.
This optimistic estimate assumes streaming reads at peak bandwidth.

| Two-loop configuration | Analytical minimum at 640-token prompt | Corresponding ceiling |
|---|---:|---:|
| Current weight formats and sequential execution | 3.70 ms | 271 tokens/s |
| INT8 head, including its row scales | 3.36 ms | 297 tokens/s |
| Perfect mixed-depth weight reuse, BF16 head | 2.67 ms | 374 tokens/s |

The last row assumes all drafts succeed, recurrent weights are read once per
committed token, and shallow/final output blocks and heads share batched reads.
It omits extra draft attention traffic, rejected computation and scheduling
costs. It illustrates how the byte model changes; it is not a speed prediction.
All calculations are in [limits.json](limits.json), generated by
[analyze.py](analyze.py). Small per-row metadata is omitted from the main-matrix
estimate, as in the existing gap analysis.

1. **Make speculative decoding the main research branch.**

   There is a direct upstream lead: the Dory vLLM PR author reports an initial
   native implementation using one loop to draft and four to verify, reusing
   early-loop KV states and activations. Its availability, implementation and
   performance still need to be established; the comment supplies no benchmark.
   [Dory implementation discussion](https://github.com/vllm-project/vllm/pull/60149#issuecomment-6168429418)

   Recent work closely matches this architecture. WaveFront advances different
   token positions at different recurrent depths in one batched recurrent call.
   LoopSpec implements related scheduling in SGLang, including branch-specific
   KV ownership, separate output-block caches at proposal depths, and CUDA
   graphs for supported branch counts. These are more useful starting points
   than another generic inference-engine port.
   [WaveFront paper](https://arxiv.org/abs/2609.23033),
   [LoopSpec paper](https://arxiv.org/abs/2609.17184),
   [LoopSpec implementation](https://github.com/kaist-flexml-lab/loopspec)

   E8 rejected a CUDA-core multi-token GEMV; it did not reject batching itself.
   Its Marlin measurements are almost flat from one to eight tokens. That is
   precisely the property needed to verify several speculative positions while
   reading weights once. Start with Marlin for batched projection work, then
   fuse the surrounding Dory operations where profiling justifies it.

   Dory's default two loops restrict the opportunity. There is only one complete
   early-loop proposal depth, and its eight-pair output block and large head
   make readout substantial. Under perfect batching, recurrent weight traffic
   falls from two block reads to one, saving 1.032 GB per token. Including the
   fixed blocks and BF16 head, weight-plus-head traffic improves by at most
   about 1.41×. For a four-loop target, this ideal ratio is about 2.22×. Actual
   gains depend on acceptance and whether output reads really share a batch.

   Do not transfer headline paper speedups to Dory: WaveFront evaluates
   four-loop Ouro and 32-loop Huginn in BF16 on an RTX A6000; LoopSpec evaluates
   Ouro and Raven on RTX PRO 6000 Blackwell. Dory has different normalization,
   fixed-block costs, low-bit kernels and only two default loops.

   The first experiment should collect shallow and final predictions on the
   **same token histories**, including the correct output-block caches. Measure
   greedy agreement, accepted-length distributions, and sampling distribution
   overlap, alongside actual times for input block, recurrent block, output
   block and head at batch sizes 1, 2, 4 and 8. Independent shallow and deep
   generations diverge and cannot supply these acceptance measurements.

   A lower-cost control is prompt-lookup/ngram speculation on repetitive code
   and text. A small external drafter is another control if a compatible one is
   available. For k draft tokens, per-token draft cost Td, target verification
   time Tv and mean emitted tokens E, the decision criterion is
   `(k * Td + Tv) / E < current target-token time`. Under independent acceptance
   probability a with a bonus token, `E = 1 + a + ... + a**k`; measure actual
   distributions rather than assuming that model.

   Preserve per-loop KV semantics for the first implementation. Retain the
   input reinjection state and early recurrent state; use separate shallow and
   final output-block caches, causal branch masks, and rollback of rejected
   positions. Last-loop caching changes historical KV values. WaveFront's
   cross-recurrence KV-sharing extension is explicitly approximate, even
   relative to sequential execution with a sharing policy.
   [WaveFront cache discussion](https://arxiv.org/html/2609.23033)

   LoopAhead is a later option: it adds a learned lookahead drafter and
   intermediate-depth feedback. Its published results do not establish a
   ready Dory drafter. First establish the training-free baseline and its
   measured bottleneck. [LoopAhead](https://arxiv.org/abs/2610.21594)

2. **Use an approximate head to screen candidates, then refine with BF16.**

   This is a proposed adaptation of the existing INT8 head. It aims to obtain
   its bandwidth benefit while retaining the original greedy decision. For
   each vocabulary row, form an effective head row `w_i` that includes Dory's
   per-token logit scale, an INT8 approximation `q_i`, and a precomputed
   residual norm `r_i = ||w_i - q_i||_2`. For hidden state h:

   ```text
   approximate_i = q_i dot h
   error_i >= r_i * ||h||_2, plus arithmetic and reference-rounding allowances
   lower = max_i(approximate_i - error_i)
   candidates = {i : approximate_i + error_i >= lower}
   ```

   Evaluate every retained candidate against the original head. Excluded rows
   cannot win if the intervals are conservative. Include equality for ties,
   reproduce the target's tie rule, and fall back to the full head if the
   bounded candidate buffer overflows. Dory's normalized final state makes the
   geometric bound particularly convenient, but measure its norm after BF16
   rounding instead of assuming it is exactly one.

   I ran a CPU feasibility check on the actual checkpoint and 16 deterministic
   random unit-norm hidden vectors rounded to BF16. The median scaled residual
   norm is 1.0104 logit units; the 99th percentile is 1.7266. With allowances
   for BF16 output rounding and FP32 dot products, the candidate set contained
   a median of 37 rows and at most 146 out of 131072. All 16 reference winners
   remained inside their sets, and all evaluated reference logits fell inside
   the pilot's intervals. Estimated weight-plus-metadata traffic was 50.2% of
   a dense BF16 head. [CPU results](head_screening.json)

   These are synthetic inputs, not Dory activations or GPU timings. They
   justify further experiments but do not establish production performance. The GPU
   implementation needs conservative bounds matching its reductions, scale
   rounding and reference arithmetic. The current vLLM head rounds dot
   products to BF16 before applying vocabulary scales; matching ideal FP32
   logits alone does not establish matching that reference.

   First replay real hidden states from diverse prompts, then implement
   device-side screening, compaction and candidate evaluation. A reasonable
   experimental goal is to recover much of E7's measured 0.35 ms benefit for
   greedy decoding. Certification and candidate handling consume some of it.
   Top-k selection can use a corresponding kth-place lower bound. Full log
   probabilities and top-p sampling still require the full normalizer or a
   separate correctness argument; an exact greedy winner does not supply it.

   CSV-Decode supplies related geometric certification ideas, using vocabulary
   clusters instead of quantization residuals. Its reported end-to-end speedups
   should not be imported here: completely removing this 14% component would
   cap whole-step improvement at about 16% on the reviewed profile.
   [CSV-Decode](https://arxiv.org/abs/2511.21702)

3. **For longer contexts, compress the full-attention KV cache first.**

   With two loops, the full-attention contribution grows by 57344 bytes for
   every additional context token; sliding layers stop growing at their
   window. The following values are byte estimates, not long-context runs:

   | Prompt tokens | BF16 KV read per output token | Sequential BF16-head ceiling | Ideal saving from halving only full-attention KV bytes |
   |---:|---:|---:|---:|
   | 640 | 0.154 GB | 271 tokens/s | 0.019 ms |
   | 8192 | 0.648 GB | 239 tokens/s | 0.234 ms |
   | 32768 | 2.057 GB | 179 tokens/s | 0.933 ms |
   | 65536 | 3.936 GB | 134 tokens/s | 1.865 ms |

   Test calibrated FP8 for full-attention layers while leaving sliding layers
   in BF16. The official vLLM documentation supports selective layer skipping,
   but support must be checked in the pinned checkout and selected backend.
   The present fused path explicitly requires a BF16 cache, so changing the
   serving flag alone disables that path. Extend the fused reader/writer or
   measure the complete fallback before drawing conclusions.
   [vLLM KV-cache documentation](https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache/)

   The vLLM team's FP8 investigation identifies head dimension 256 and small
   sliding windows as important performance exceptions, with prefill costs
   and quantization overhead that can outweigh gains. Its Hopper/Blackwell
   results do not establish Ada performance. KIVI's separate treatment of key
   and value quantization is a useful design reference, but Dory's normalized
   keys require fresh calibration and long-context quality measurements.
   [vLLM FP8 analysis](https://vllm.ai/blog/2026-04-22-fp8-kvcache),
   [KIVI](https://arxiv.org/abs/2402.02750)

   Last-loop caching can reduce cache capacity from 56 to 36 attention
   applications at two loops, but all loop computations still run and read
   history. It does not automatically remove 36% of decode KV traffic, and it
   changes predictions. Its chunked-prefill semantics also require validation.
   [NVIDIA model card](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16),
   [llama.cpp Dory PR](https://github.com/ggml-org/llama.cpp/pull/30306)

4. **Keep kernel research targeted at measured costs.**

   The theoretical 3.70 ms floor leaves 1.36 ms relative to E9. Of that,
   about 0.90 ms is in fused weight projections and 0.28 ms in attention.
   A plausible engineering target for unchanged formats is roughly
   4.2–4.5 ms at this profile point, not an assurance. It corresponds to
   projections near 85–90% effective bandwidth, attention around 0.25–0.30 ms,
   the current head, and around 0.10 ms of other work. Beyond that, prioritize
   reducing traffic rather than accumulating small fusions.

   Profile the gate/up and combined QKV/gate kernels first: together they take
   about 2.39 ms. Inspect DRAM bytes and throughput, L2 traffic, register spills,
   occupancy, instruction issue and dependency stalls. Then test CUDA or
   Triton-generated code changes to FP4 unpacking, vectorized loads, reduction
   scheduling and overlap. GemLite offers relevant small-batch kernel designs,
   but its INT4 layouts and scaling do not substitute directly for Dory's
   group-16 E2M1/FP8 format. [GemLite](https://github.com/dropbox/gemlite)

   A concrete short-context attention probe is a SIMT implementation for the
   four query heads per KV head. The current tensor-core path pads that group
   to 16 rows, including the raw-query normalization work. Avoiding that padded
   state may lower register costs. Keep the existing tensor-core path where
   longer contexts favor it, and test complete attention-plus-output timing.

   Another small experiment is to have the producing projection finish only
   the residual reduction scalars, then reconstruct the residual input while
   the next projection loads it. This could remove part of the final vector
   materialization without programmatic dependent launch. It adds activation
   loads and arithmetic, needs bounded buffer lifetimes and correct BF16
   rounding, and may lose; benchmark one sublayer boundary before expanding it.

   Persistent execution remains a larger option for cross-operation memory
   overlap and synchronization. Small idle gaps do not measure kernel
   prologue/epilogue costs or stalls inside busy kernels. However, eliminating
   only the observed idle time saves about 0.04 ms, under 1% of the step.
   FlashFormer and Mirage offer designs to study, not established Dory/Ada
   speedups: FlashFormer's evaluation is on H100, and Mirage's paper evaluates
   A100, H100 and B200. Prototype a persistent MLP or layer pair before a whole
   decoder, and use a resident cooperative grid or another proven scheduler.
   An oversubscribed grid with spinning global barriers can deadlock.
   [FlashFormer](https://arxiv.org/abs/2505.22758),
   [Mirage](https://arxiv.org/abs/2512.22219)

   CUDA programmatic dependent launch requires compute capability 9.0 or
   later; it cannot be enabled on this SM89 GPU. L2 persistence controls exist
   on this architecture, but one recurrent block is 1.032 GB, far above the
   4090's 72 MB cache. They cannot retain the whole block across loops. The
   existing E6 prefetch result is a realistic guide to the smaller opportunity.
   [CUDA dependent-launch requirements](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html),
   [CUDA L2 controls](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html)

5. **Preserve serving capacity and evaluate completed-task latency.**

   The fused weight copy consumes 1.85 GiB and reduced available KV cache by
   10.7% in the serving confirmation. At 64 users with long prompts, median
   time to first token rose from 3.6 to 5.1 seconds despite similar aggregate
   throughput. A shared layout for batched and single-token kernels would
   recover this capacity; it is a substantial serving improvement even if
   single-user decode time stays flat. Speculative branches and an additional
   INT8 head must be included in the memory accounting.

   Treat activation sparsity and lower-bit body weights as separate quality
   experiments. SiLU/SwiGLU does not supply ReLU-like exact zeros; thresholding
   small activations changes the model. Dory's normalization can also change
   how those perturbations propagate. TEAL provides a useful starting point
   if this quality tradeoff is authorized, with block layouts needed to turn
   sparsity into fewer memory transactions.
   [TEAL](https://arxiv.org/abs/2408.14690)

   The NVIDIA model card says extra loops can reduce generated token counts.
   Compare time to a correct completed answer at a fixed quality level, not
   only tokens/s: `prefill time + output-token count * decode-token time`.
   A request-level choice among fixed loop counts is an uncomplicated first
   experiment. Per-token adaptive depth with per-loop caches needs a solution
   for the missing historical KV entries at depths earlier tokens skipped.

The engine investigations support keeping the current vLLM integration as the
reference. Its Dory PR remains open at the pinned implementation reviewed here;
llama.cpp's Dory PR is a draft with CUDA correctness evidence but incomplete
long-context qualification. The GitHub searches did not establish a ready Dory
integration in SGLang or TensorRT-LLM; this is a search result, not proof of
absence. TensorRT-LLM's FP4 dispatch discussion also confirms the relevant
hardware distinction: Ada uses a weight-only route such as Marlin, rather than
native FP4 tensor cores. Changing engines alone does not change the byte floor.
[vLLM Dory PR](https://github.com/vllm-project/vllm/pull/60149),
[llama.cpp Dory PR](https://github.com/ggml-org/llama.cpp/pull/30306),
[TensorRT-LLM FP4 dispatch discussion](https://github.com/NVIDIA/TensorRT-LLM/pull/12591)

The next three proposed experiments are: same-history loop-1 versus loop-2/4
acceptance and component timings; real-activation head screening; and calibrated
full-attention FP8 KV at 8K and longer contexts. Continue the existing 16/64-user
regression gate, record cache capacity and TTFT, and retain the 64-prompt
numerical comparison. New quantization or approximation claims additionally
need task-quality and long-context evaluation; the current near-tie agreement
gate alone does not establish those properties.
